# オートメーション実行基盤とコマンドゲートウェイ

## 概要

Synvelis の Automation 系と Command Gateway 系の設計・実装で確立された契約と検証規律をまとめる。Automation 系は `synvelis-workspace`/`synvelis-project` の headless 状態機械・曲線処理・記録 transaction（AUT-01〜04 = synvelis#131〜134）、Automation/Modulation 統合 Parameter Control の設計契約（synvelis#6）、AUTX の Action/CLI/Macro/Workflow 系（synvelis#259〜267・#446）からなる。Gateway 系は `synvelis-gateway` クレートの capability 契約・認可・context projection・prepare/proposal/commit・Job/Media/Provenance・MCP adapter・UI contract・E2E evidence harness（synvelis#45・#46 の設計契約と、GW-01〜10 = synvelis#53〜62 の実装記録）で構成される。

両系統に共通する設計原則は、単一の権威への集約（第二の registry・validator・writer・正本を作らない）、fail-closed と型による状態分離、そして headless/mock の検証結果を製品受入へ昇格させない証拠規律である。

## 詳細

### Automation の mode 状態機械と writer transaction

Automation mode は Off/Read/Touch/Latch/Write の境界状態機械として `ControlSession` に実装された（synvelis#131、AUT-01）。Touch gesture の release 後は manual override を外し、`v = v_release + (v_automation(t) − v_release)·w`（`w = 3x² − 2x³`、`x = clamp(elapsed/return_duration, 0, 1)`）の Smoothstep 補間を session clock で駆動する。return 時間の既定は 150 ms の暫定値である。Touch Return は Automation Point の追加・削除・書換・ProjectRevision 変化を伴わない runtime-only の復帰であり、`ReferenceSource::Return` variant が `synvelis-project` に追加され、session が注入する pre-modulation reference 領域の runtime blend マーカーとして永続カーブの評価結果と型で区別される。`v_automation(t)` は評価位置ごとに現在の series を再評価するため、Return 区間中のカーブ編集と Step/Linear 双方に追従する。

gesture は `gesture_begin` 時点で `ControlGestureFixation`（target/lane/revision/scope/epoch）を固定する。writer は境界イベント（transport stop/seek/wrap・play edge・focus 喪失・plugin crash・target 消失・project 変更）で明示的に閉じられ、閉鎖理由は `WriterCloseReason` で型化される。transaction 自身の commit を foreign change と誤認しない self-seal 回避が契約化された。`record_start(project, revision)` は Arm+write-mode 固定集合の Write target に reference 基準値を `manual_overrides` へ seed し、pre-modulation 値を verbatim に保持する。domain 外の開始位置では transaction 作成を abort せず target を unheld に留める挙動が確定した。

Region Replace（synvelis#132、AUT-02）では、`cut_range_points` を per-lane の機械的切断 primitive として不変のまま残し、anchor 計画と stitch を op apply 層に置いた。評価が target 全 lane の merged series 上で行われるため、境界値・host 選択・重複挿入抑止も merged 基準に揃える必要があったためである。`BoundaryAnchor{pos, value, interp, source}` は pre-edit merged series から `(left, right)` を計画する純粋関数で、`value`/`interp` は旧系列の `v_old(cut)` と segment interpolation、`source` は post-edit merge-skip 判定に使う旧 chase 源 triple である。左 anchor は新 region 先頭へ畳み込み、右 anchor は post-edit で stitch する。同時刻の明示 point と `q_S` 不在は計画時点で除外し、Ownership（明示 point が境界を所有し、sentinel は明示 point 非存在時のみ）により構造上の競合を排除する。`stitch_boundary_anchor` は post-edit の chase 源が `source` と一致すれば skip し、他 lane 残存・N 自身の point が triple と一致する silent 重複を防ぐ。host region への挿入は interp 一致なら昇順挿入、不一致なら host 分割で sentinel region を作り、host 不在なら fallback lane に sentinel region を追加して regions Vec は `range.start` 昇順を維持する。host region 縮小は host 先頭 point pos に限定して `validate_references` oracle で強制検査し、sentinel region は `end = min(s_next, pos+ε)` で上限固定、f64 の `[0,1]` 境界割れは挿入時に clamp する。

Loop 録音（synvelis#133、AUT-03）の製品契約は「1 Loop Pass の半開区間 `[first point, coverage)` で終了・Transport は続行可・後続 pass の自動書込みなし・明示 Rearm」である。録音経路の境界処理は `seal_recording`（廃止）から `close_write_range(project, reason, bound)` 一本の共通経路へ再編され、wrap/stop/seek/play-edge/loop-change/epoch-change/graph-stale/project-change/mode/arm の 10 の seal 経路が全て同関数を通る first-seal-wins となった。境界では in-flight gesture の delivered points を `pos <= bound && pos < loop_end` で clip して append し、記録済み点は pass の一部で preview ではない。active writer が居た fixed lane へは `coverage_end[lane] = bound` を project beats で記録する（held write の連続被覆末尾は `last point + ε` で表現不能なため別列）。`bound` は wrap 時のみ loop end、他は閉鎖時点の transport position で、loop 設定時は `min(bound, loop_end)` に clamp する。`PlaybackState.pass` は play edge で 1、wrap 毎に +1（saturating）、pause/resume/seek/stop では不変。後続 pass の自動再書込みはせず、明示 `record_start` がその時点の pass を fixation する。`RecordingTransaction.{pass, fixed_scopes, coverage_end}` を record_start で fixation し、`txn_fingerprint` を拡張して prepared commit の identity に AUT-03 context を含める。`record_write` は `pos >= loop_end` を Validation 拒否し、gesture batch 経由の `record_points` でも同境界で clip する。`bind_write_lane` は open tx 中の fixed target rebind を拒否する（mapping は record_start の写しが不変の正本）。`prepare_record_commit` は lane 毎に `coverage_end` を fixed scope で scope 座標へ resolve し、`> last_pos` の時だけ Replace range の exclusive end に採用する（resolve 不能は last+ε fallback で、silent な範囲捏造はしない）。

### 非破壊 viewport LOD と bounded RT キュー

AUT-04（synvelis#134）の source truth は `Project::control` の merged series のみで、LOD は永続データを持たない揮発 projection である。`automation_view` は viewport `[start,end]`（scope 座標の lossy f64 表示軸）を bounded 縮約し、`ViewBin` の厳密 min/max envelope を提供する。bin は半開で最終 bin のみ end を含み、Linear は affine のため端点+内部点で厳密に評価でき、未到達 bin は `covered=false`+NaN で 0 や補間値を捏造しない。

`CurveFeature` は `StepEdge`（入る点でなく前 segment の interp 起点）・`Extremum`（厳密方向反転）・`RegionBoundary`（AUT-02 の sentinel anchor も捕捉）を `BeatPoint` 正確保持で分類し、verbatim 点 channel と `CurveQuality`（`Exact/Reduced/Truncated`）を持つ。

RT 経路は `record_event_rt` が `ruviform_rt` SPSC への `try_push` のみで構成され、成功・invalid-reject 両パス 0 alloc を stats_alloc で計測 pin する。`drain_record_events` は非 RT・event budget 有界で、`WrongTxn/GatesClosed/OutsidePass/BadValue/ScopeLost/LaneGone/OverBudget/Failed` を `RecordRejectKind` で型分離し silent drop しない。`RecordTargetHealth` は target 毎の dropped/queue_fulls/overflowed/rejected + gap run + notified_fulls watermark（QueueFull 通知は drain 毎 1 回・delta のみ）を持つ。drop run は tx の `record_gaps[lane]`（project beats、view で scope resolve）に fold し穴を曲線として捏造しない。cap 超過は末尾 merge + `record_gaps_merged`/`record_health_overflows`/`record_notifications_dropped` で観測可能にする。`AutomationLaneView` は model LOD + pending overlay + deliveries + gaps + health + revision の read-only projection で、`&self`+`&Project` のみで Project/revision/undo/build を変化させない。

### Automation/Modulation 統合契約の位置づけ

synvelis#6 は製品 UX・設計仕様を文書チェーン 7 文書（spec/design/plan/task/test-spec/impl-ir/impl-exp）と受入被覆台帳として固定した docs-only slice である。`completed` は文書チェーン作成の完了を意味し、crate/UI/CI/Cargo/mise 設定の変更はなく製品実装の完了ではない。実装は下流 Issue（PC-C1〜06 = synvelis#98〜103、CTL-01/02 = synvelis#121/#122、AUT-01〜04 = synvelis#131〜134、GUI/実機 = synvelis#102/#114/#103）が Owner である。

設計上の正本は `ControlOwner × AutomationTimeScope` の直積と `ParameterTargetId` であり、旧 Scope 表を新型の代用品にしない。第二の `ControlModel` schema・第二 Persisted Control Engine・RT 上の可変割当の作成が明示的に禁止され、value provenance は 7 層で分類して pre-modulation recording を扱う。AM-01〜13 を既存 headless テストへ写像し、`Pass (headless)`/`Partial`/`NotRun`/`Deferred`/`Unsupported` で分類する。設計のみの項目は Pass にせず、headless 証拠を GUI Pass と誤記しないことが検証・受入ポリシーとの整合要件である。Touch Return 時間・LOD 密度・精度などの数値は根拠なき契約を避け、既存契約参照か PoC 後委譲に限定する方針が Decision Log に記録された。

### AUTX: Action Catalog・CLI・Macro・Workflow の権威境界

AUTX-01（synvelis#260）の Action Catalog は descriptor/schema/presentation からの projection-only であり、lifecycle status・schema consistency・executor verdict を分離する。orphan presentation は typed unknown/unsupported-version entry として可視のまま残し、catalog mutation API と権威 field の複製を持たない。後続の synvelis#446 は `CapabilityRegistry::has_executor` 読み取り専用 accessor（`&self`・bool・内部状態非変更）を追加し、`ExecutorState` を `Installed`/`Absent`/`Unknown` の 3 verdict に拡張して No-Handler を `Unknown` と区別した。`Gateway::invoke` の `NoExecutor` authority・`handler` の `pub(crate)` 境界・`automation_ui` view 契約は不変で、synvelis#272（`Gateway::schemas()`）が前提依存である。

AUTX-02 の CLI adapter は、TTY・`--yes`・環境変数・CLI JSON のいずれも human を証明しないと定めた。human authority は credential-backed verified session が必須で、unattended call は delegated/agent call として既存 grant policy を invocation 毎に再利用する。認証失敗は専用 `GatewayError::Authentication` で区別する。CLI mutating invocation は synvelis#261 の Auth/Host Gate まで非公開である。

AUTX-03 の headless CLI は fail-closed を基本形とし、action list/describe は read-only registry projection、prepare/invoke は `HeadlessSessionHost`→sealed caller identity→`Gateway::handle` の経路を通る。file extension mapping は deterministic で fail-closed、CLI envelope と exit code mapping は集中化され、`render` は real provider なしで unsupported である。実害として、`--format json` が human output を返す bug（global flag pre-scan が `--` prefix を剥がさない）、`DirectoryBundleStore::create` が dry-run/read-only や非 bundle dir で `snapshots/` を作る副作用、read-only boot が `live_revision` を失い `expected-revision: 0` に落ちる問題、top-level `target` が prepare request に混入し `TargetContract::None` で `UnexpectedTarget` になる問題が修正された。

AUTX-04 の Atomic Macro は共有 AST に `$param`/`$output` 式 variant を追加するが通常 workflow では拒否する。composite validation は当初 pre-state で全 member を評価していたため create-then-reference が `NotFound` で失敗し、F01 で project validation を scratch clone + 順次 validate/apply に修正した（`PreparationRejected` typed）。F02 の Gateway 側 binding は member-order trial apply・`resource_map` diff・scratch-backed provisional authorization oracle を採用し、`peek_raw_id` による ID 事前計算は operation variant が複数 resource を mint し reservation window で sequence がずれるため却下された。failed member apply は trial clone を使い成功済み先行状態を保持する。watermark-seeded dry-run には外部 reservation が generator を進めて commit しない場合に fail-closed になる制限があり、Gateway placeholder resolution へ委譲された（accepted limitation）。

AUTX-05 の Workflow DSL は汎用 YAML 依存を避け制限付き custom YAML parser を採用した。anchor/alias/tag/flow collection/duplicate key/multiple document/noncanonical number/resource-limit violation を全て拒否し、Workflow AST は任意 script/eval/function-call 権威を持たない。静的 budget は保守的（branch 最大値/union・bounded loop 乗算・明示 compiler ceiling）で、digest は canonical sorted JSON の SHA-256 である。

AUTX-06 の Workflow Coordinator は replayable Run/Step FSM・journal-first 遷移・resumable cursor・fault fixture を持つ。`retry_policy` が journal のみでなく in-memory にも保持され cold replay で消失する問題は `JournalEntry.retry_advice` 追加で digest/replay path に含めて修正した。live adapter は delegated principal のみ attest し、human workflow は credential-bearing step call なしに fail-closed である。`operation_result` reconciliation は outcome ledger→commit reconciliation→job records の順。registry snapshot は exact version/schema を保持し "latest" を解決しない。mixed-source（YAML/Luau/Rhai）run は semantic journal・projection・lane-call signature を比較し、plan digest は witness であって parity gate ではない。

AUTX-07 の GUI views は GUI projection を workspace 側、app 側 ViewSpec 生成を別に置き、GUI は authority も第二の project/grant/job truth も持たない。Action Palette・Macro Browser・Workflow Editor・Run Monitor は driver-neutral で、category 選択は Tabs でなく buttons（重複 component key 回避）、Workflow Editor v1 は display-only、`JobCancel` は unique capability を解決し confirmed cancellation を捏造しない。`AutomationCatalog` は serde-neutral で注入し publication は deep `PartialEq` でなく revision stamp で行う。

AUTX-08 の same-wire 3-surface parity は GUI・local CLI・MCP surface が同一 wire semantics と typed outcome parity を持つことを検証した。Leg C は production `GatewayStepLane` を fresh `rig::compose()` stack 上で組み立て、Leg B と同一論理操作の `StepCall` に対し outcome/error/`DuplicateRequest`/`operation_result` reconcile の 4 assertion parity を固定した。private `step_wire` bytes は直接 assert せず公開 `StepLane` surface が正当な証明面である。`GatewayJobLane` は Leg C slice では未実装で coordinator/job integration は scope 外である。

### Command Gateway の単一権威と証拠規律

Command Gateway（synvelis#45）は capability discovery・schema/version contract・authorization・context projection・operation preparation・proposal/approval・commit gating・idempotency・jobs/media/provenance・MCP integration・evidence reporting の単一権威経路である。adapter と GUI は第二 registry・重複認可・実行/確認状態の捏造を持たず、Project が project/undo 意味論の単一 writer であり、Job・Media・semantic diff・transport receipt は別 owner である（synvelis#45）。

要求状態（`Required`/`Deferred`/`NotApplicable`）と実行結果（`Pass`/`Fail`/`NotRun`/`Unsupported`）は別軸で記録し、mode（mock/real）・layer（L1〜L5）・`required`・`real_only` を保持する。headless/mock/PoC real transport の Pass を製品受入・実 GUI/OS/provider/第三者 host 受入に昇格させず、`NotRun`/`Unsupported` は first-class verdict で optional 欠測は gate を fail させないが記録は残る（synvelis#45・#46）。G0〜G6 各 Gate を `Headless Verified`/`Product Accepted` の 2 軸で記録し、実 GUI・第三者 MCP Host・実 Provider・実 OS lane・電源断・大規模負荷・Consumer 回帰を全 Gate で `Product Accepted = NotRun` として分離する。設計合意・Issue 起票・mock 成功・PoC transport 成功を `Product Accepted` と記録しない規則が test-spec に固定された（synvelis#46）。

case 単位の fixture/oracle/Owner/mode/layer/status の詳細写像は sv45 の case ledger を正本とし、sv46 の受入照合台帳は Gate 受入条件への照合に限定して参照する構成で、複写・二重管理を回避している。`src/evidence.rs` の MATRIX（case→gate/owner/required/real_only）が canonical case 一覧の正本である（synvelis#45・#46）。

MCP transport の第一候補は Local stdio Helper + 認証 Local IPC だが未確定（synvelis#46「まだ最終決定しない」を維持）で、Localhost Streamable HTTP は比較候補として残るが未実装・未比較である。MCP Tool Discovery/Schema が権限の代替でないこと（`tools/list` は bound session 必須・各 Invocation は GW-02 へ再照会）を実測証拠として記録し、AI Runtime と External MCP Access は独立 switch で分離する（synvelis#46）。`synvelis.operation.batch`（GW-04）と `ProjectOp::Composite` は既存 GW-04 の一部であり、独立 Macro Engine・別 Commit Gate を Gate 判定に含めない。AUTX #259〜267 は Gateway 契約を参照するが #45 設計 slice の完了を待たない（synvelis#45・#46）。

### GW-01〜03: wire 契約・認可・context projection

GW-01（synvelis#53）は contract wire の実装で、internally-tagged outcome は scalar/newtype payload で serialize 不能だったため named field + `status` tag に変更した。idempotency を bind 時点で記録すると denied/unexecuted key が消費されるため check/record を分割し handler 成功後に記録する。serde が nested unknown field を黙過するため wire 段で明示 scan を追加し、`deny_unknown_fields`・resource-set 上限・文字数検証・安定 error naming・`SchemaConflict`/`Denied` の明確化も実施した。wire に authority field（`selection`/`focus`/`active_window`/`current_selection` 等）は `FORBIDDEN_AUTHORITY_FIELDS`→`SelfDeclaredAuthority`、implicit target は `ImplicitTargetRejected` で拒否する。

GW-02（synvelis#54）は `PolicyEvaluator` seam 上に `GrantPolicy` を実装した。human principal は adapter-attested manual authority として全 stage permit であり、effects 検査 skip は設計意図で manual authority の attestation 経路が正しいことが前提（GW-08 以降の adapter 契約に依存）。agent は live task（activation; proactive は live permit 再照会）+ principal/project/binding 一致 grant の両方必須で、binding 証明前の失敗は一律 `no applicable authorization`、scope 失敗は `target outside grant scope` で存在情報を漏らさない（existence-blind）。`DataAccessClass`（MetadataRead/MediaBytesRead/StructuredContentRead/WorkspaceSelectionRead/DerivedDataRead/ExternalDisclosure/ProviderTransfer）で descriptor ⊆ grant を評価し、`ScopedEffects` の unsupported 非空は一律 deny。`ResourceFacts::Unresolved` は不在と不可視を区別しない。`PolicyStore` trait は grant/task/proactive_permit/policy_epoch/`try_consume_apply` の全てを単一原子操作とし、`try_consume_apply` は write lock 内で存在/liveness/epoch/budget を再検証してから消費する（TOCTOU 排除）。authority ID は単一発行で再発行は no-op（revoked/consumed を巻き戻さない）。review で確定修正: apply budget が評価呼出回数で消費（preflight で N commit が underwriting）→ unit を `evaluate_commit` の原子消費に。`max_members` が target/effect で二重計上 → `ScopeCounters` を per-request 1 本化し `ResourceRef` 単位 dedupe。descriptor-vs-request の id+version 未照合 → `evaluate_with` 冒頭で検証。issue 再発行で revoked/consumed 巻き戻し → `entry().or_insert()` 化。`try_consume_apply` の liveness/epoch 未再検証 → write lock 内再検証。`_ => PermitForStage` ワイルドカード fail-open → 既知 stage 全列挙。`InMemoryPolicyStore` は mock で durable store・commit fence・recovery は GW-06 へ defer。

GW-03（synvelis#55）は `SnapshotSource` seam 経由で commit 済み Project 状態を pin し第二の正本を作らない。`PinnedSnapshot` は `Arc<Project>` 共有不変参照である。scope admission は pin 済み `ProjectOracle` で評価し data と同一 revision に揃える（live oracle との false admit/deny・存在 leak を防ぐ）。cursor は TTL・rotate・caller/adapter/task/grant/snapshot/fields 結合で、continuation は lock 内で authorize+consume+rotate を原子化し、純粋な `project_item` は lock 解放後に行う。失効 snapshot は `SnapshotExpired` で Latest への silent fallback なし。`Completeness` は complete/unknown/unavailable の 3 値で正直に報告し（media は descriptor のみで PCM bytes 非 emit、derived source 不在は `unavailable`）、review で確定修正: range filter が scope admission より先に走り out-of-scope 存在/配置 probe が可能 → `candidates`（selector のみ）と `range_filter` を分離し admission 後に適用。scope admission が live oracle facts で評価され data は pin から読む → `ProjectOracle::new(pinned.state)` で同一 revision。`project_selection` が `pin_for` を再呼出し item と selection が別 revision を混在 → pin 済み `Arc<Project>`+oracle を受渡し 2 度目 pin を構造的に除去。`SnapshotSource::pin` の lock 下呼出 → lock 外 fetch+re-check で競合 dedupe。pin-absent selection member の無言 drop → completeness は filter 前 member 集合で判定。pin/cursor retention は engine 全体の共有 quota（per-principal は GW-08 契約待ち）。`TypedRange` は time-base field を持たず media-domain の `clip_window`/`item_window` は per-value base 混在を避けるため `None`（canonical base 契約待ち）。

### GW-04〜06: semantic prepare・proposal/approval・commit gate

GW-04（synvelis#56）は domain legality を `Operation::validate` に一元化し AI 専用の第二 validator を作らない。validate は pin 済み clone 上で走らせ live は不変、apply は private clone のみ。Effect は `Observed{attrs, detail}` の 2 層観測から導出する（`ResourceAttributes` だけでは muted/velocity/`SourceState`/name/ppqn/tempo map を観測できないため entity 全体の serde 値を detail にする）。unsupported は `PreparationRejected` で caller 非依存 fail-closed（human early-permit を迂回経路にしない）。transaction 内生成 resource の parent 解決は base-first oracle（base ∪ candidate、base だけでは Unresolved deny、candidate だけでは delete 済み resource を見失う）。inner mutation descriptor に executor を置かず apply は GW-06 まで存在しない。linked MIDI は source-level note op が `impacted` で shared source Write references に全 linked clip を列挙し implicit copy なし。batch は単一 `ProjectOp::Composite` で member 失敗は全体 reject（1 Composite=1 undo）。review で確定修正: MIDI note payload が metadata-only emission class で漏洩 → `emitted_classes` で note detail を持つ effect を structured-content class に分類。domain `NotFound` が scope 認可より先に走り absent/out-of-scope を識別可能 → provisional scope gate を `op.validate` より前へ（両者が同一 `Denied` verdict）。batch member args の schema 検証迂回 → 共通段へ移動。batch capability 自体が authorization floor に非含有 → executed operation ref を floor に追加。nested `target` 未知 key 黙過 → `wire.rs` に shape 別 allowlist。project-level create の `parent` が request project と未照合 → `provisional_gate` 冒頭で検査。`CapabilityRef` version 不一致が `UnknownCapability` に丸まる → `UnsupportedCapabilityVersion`。precondition が generic → `Operation::validate` の実前提を mirror。

GW-05（synvelis#57）は `PreparedChangeSet` を canonical 化（JSON object key ソート）SHA-256 `ContentDigest` で bind する。digest 入力は schema/schema_version・base{project,revision,tempo_map_revision}・commands・preconditions・effects・unsupported のみで、proposal/operation/request ref・caller・task/grant・snapshot ref・時刻・保持順序は意味的同一性に入れない（GT-007）。preview は第二 diff engine でなく GW-04 の DerivedEffect 射影であり、digest が bind する内容と preview が乖離しない。receipt は proposal の記録済み identity に bind し（wire 自己申告値は使わない、GT-008）、`ProposalStore` 単一 lock 権威で proposal/approval/apply の 3 状態機械を `transit` データ一元化する。consume は受理と同一 lock で atomic（`accept_apply` で verify+spend+record を一括）。wire `approval` arg は correlation であり権威ではない（`approval-for-<operation>` は提示用参照、権威は receipt binding）。受理済み apply は proposal 死亡から独立（`AwaitingApproval` は proposal と共に Reject するが `CommitRequested` は GW-06 の settlement 対象）で、終端 apply の後だけ承認 lifecycle を再開可。`settle_apply` は commit 側 event のみ受理（`Accept` は apply gate の遷移）。bounded 保持は terminal entry を優先退避し全 entry live なら `LimitExceeded` backpressure（live entry を黙って捨てない）。review で確定修正: lazy expiry/eviction が受理済み `CommitRequested` apply を `Rejected` へ書き換え → cascade を `AwaitingApproval` のみに限定。liveness 検査と record 作成の競合 → `accept_apply` で store lock 下 atomic 化。dead proposal への lifecycle record 成長 → `Prepared` でない entry に記録を作らない。receipt 再消費冪等性未定義 → `consume_in_entry` 集約（同一 operation+同一 receipt のみ verify-冪等）。終端 apply 後の Consumed receipt 恒久詰まり → apply terminal のみ request 再開。bounded FIFO が live proposal を退避 → terminal entry 優先 victim、全 live なら `LimitExceeded`。`settle_apply` が `Accept` を受理 → commit 側 event のみ受理。preview descriptor の data_access floor が過剰 → floor を `MetadataRead` に下げ実 bound は `emitted_classes` を emission boundary で検査。失敗 attempt が live apply record を上書き → `fail_apply` は live record がある限り記録しない。

GW-06（synvelis#58）は最終認可（commit-stage `evaluate_effects`・`ApproveToApply` receipt 再検証・delegated apply budget の atomic spend）を経て既存 `ProjectController::apply` 単一 writer で commit する。「Gateway に第二 Writer を作らない」制約の下、revoke・commit・save・undo/redo を同一 `CommitFence` で直列化する。revoke-first → commit は revoked grant を観測して deny、commit-first → mutation は残り revoke は undo しない（両ケースを ScheduledFence で決定的に検証）。idempotency identity は `(principal, project, key)`+fingerprint で、request/operation ID は retry 毎に変わるため fingerprint から除外し、capability/project/target/args/consistency/task/grant が同一なら durable outcome を replay、異なれば `IdempotencyConflict`。transport 復帰は commit 確認にならず journal persistence が権威であり、apply 後 journal 前 crash は `Indeterminate` で `reconcile` が実 outcome を引く。undo/redo も gate+fence+journal 経由（history 遷移自体が新 revision の commit で revoke との直列化を逃れない）。`Committed` は replay で終端（後続 `Indeterminate` で上書きしない）。HEAD/snapshot だけから commit を推測しない（journal に outcome の無い apply は `Indeterminate`）。`FileJournal` は magic `0x4A4A`+version+seq+len+payload+CRC32 の 16B header フレームで append は `sync_data` 永続化、open は replay scan で torn tail/bad magic/checksum 破損/seq gap を検出し intact prefix を保持して破損末尾を切詰める。採用 PoC は A=単一 ordered commit+policy journal（recovery ordering を seq で完全復元）、B=independently durable `FilePolicyStore`（policy log と commit journal の cross-LSN 記録で A/B の recovery ordering を比較可能、durable admin 配下では独自 log が権威で二重消費しない）。サポート対象外を明示: fsync が嘘をつく storage・検出不能な silent bit rot・journal GC/checkpoint・複数 project multiplex。review で確定修正: `ApprovalRequired` を無条件 reject → consumed receipt を fence 内で verify-冪等再確認した場合のみ Proceed。`AwaitingApproval` が `Indeterminate` 経路に乗る → `Denied`。replay で後続 `Indeterminate` が durable `Committed` を上書き → `Committed` 終端保持。`FilePolicyStore::mutate` 閉包 no-op → inner store 実更新+durable record。`Box<dyn IdGenerator>` 非 Send → `IdGenerator: Send` 追加。`FileJournal::append` が write/sync 失敗時 partial bytes を残置 → offset 検査。`OperationId` 衝突（manual/undo/redo の synthetic id が replay `by_operation` と衝突）→ `CommitRecord.operation` を `Option` 化し非 apply commit は `None` で ledger 不登録。

GW-07（synvelis#61）は Job 状態の権威を adapter 側 `JobBook`（bounded・same-scope eviction・existence-blind scoped lookup・grant 別 budget 計数/revocation sweep）に置き MCP session `Unconfirmed` で `Cancelled` を名乗らない。`synvelis.job.submit` は `StartAsyncOperation` stage で `evaluate_effects`（input scope+`ProviderTransfer`）→input snapshot→`limits.job_budget` admission GW-08（synvelis#59）は trusted local connection を explicit connection permit で確立し `synvelis.connect` が唯一の credential 経路とする。verified permit record + adapter attestation(seal)から `CallerIdentity` を構成し、MCP `clientInfo`・agent 自己申告・tool 引数は trust に一切寄与しない。session は `McpChannel::Client`(agent)/`Control`(human) に分離し、許可失効・kind 不一致・unknown secret は同一 blind `PERMIT_INVALID` verdict で閉じる（verdict 差異は permit existence と状態の oracle になる）。control method は client channel で method-not-found（discovery 自体を絞る）。tool discovery ≠ execution permission で、各 call は `Gateway::handle` が grant/policy/disclosure を再評価する。`wire_for` が唯一の wire producer で task/grant 注入・consistency・typed ID を一箇所に集約する。`proposal.apply` は accepted handle+`CommitPort::commit`→`reconcile` で durable verdict を報告し retry は settle 済み verdict を返し再 apply しない（duplicate commit 防止）。op handle は (principal,project,task,grant) owner scope+blind（foreign handle は `unknown-operation` 一択）。`operation.cancel` は `CommitGate::cancel_apply` で fence 直列化し負けた場合は実際の settled status を報告する。adapter は `enabled:false` 既定で MCP 無効でも DAW 独立動作。transport は PoC(stdio+loopback TCP)で production transport 決定は scope 外。境界: control listener は loopback+permit 認証の PoC posture に留まり remote exposure・mutual-TLS は未対応。`FilePermitStore` は secret hash を永続化するが store file 自体の ACL/integrity は host 環境責任（tamper detection は hash mismatch→invalid permit で fail closed、integrity 署名は未実装）。real-transport で検証したのは line-oriented stdio+loopback TCP の 2 channel で Streamable HTTP/remote transport は未実装・未検証。

### GW-09〜10: UI contract と E2E evidence harness

GW-09（synvelis#60）は UI が authorization truth を持たず、adapter attestation 経由の bound `CallerIdentity`+明示 id のみを GW-02/05/06 へ渡す。UI state は権威 record の投影+UI bookkeeping（UI が truth を複製しない）。approval surface は `(proposal, digest)`+reviewed base revision に pin され、mis-approval（selection churn・other-window・proposal swap・wrong digest・expired proposal・revoked grant）を全て拒否する。mode は issued grant の `ApprovalPolicy` から派生し UI が自己申告しない。revocation = intent→confirmation の 2 段階で job cancel と分離（grant/connection revoke が job cancellation を暗示しない）。accepted apply ≠ commit ≠ engine ≠ saved を別軸で報告し、AI runtime と MCP adapter は独立 switch である。fixtures は GW-08 rig と同型の real seam（real `Gateway`/`ProposalGate`/`CommitGate`+journal）で mock 出力でない。workspace に配置される（gateway crate は UX を持たない GW-01 ADR 境界と整合、依存方向は workspace→gateway 一方向）。境界: `GatewayUi` の row/surface は権威 record の投影+UI bookkeeping で `note_*`/`refresh_surface` を host が呼ばない限り表示は stale になり得る（push 型 subscription は scope 外）。ただし stale 表示が authorization を迂回する経路はなく最終判定は常に GW-02/05/06 側である。real-device GUI render・focus・multi-window race は manual gate で未検証。

GW-10（synvelis#62）は期待値 Oracle を実装と独立に保つ（`GrantPolicy`/`ProposalStore` の内部型を共有せず decision class（Permit/Deny/ApprovalRequired/Conflict/Unknown）のみ比較 — 「第二の Policy/Project 正本」を作らない）。`MATRIX` が case→gate/owner/required の唯一の正本で、test 側 `.meta()` に gate を渡させず matrix row から導出する（record が自らの帰属 gate を偽る経路を API 境界で閉じる）。`.owner()`/suite-level fixture は API から削除し fixture は case 毎の必須設定。並行は race ではなく `ScheduledFence` で列挙（commit section を park、driver が両順序を明示 release、thread 完了順も join で確定）。実 transport(mcp-poc)と in-process は crate を分け mode=real/mock を正直に記録する。optional 行は `required=false` で NotRun 記録し gate は required のみ。`real_only` 行は `mode="real"` の record のみ集計（mock Pass が real coverage にすり替わる経路を matrix 層で構造的に閉じる）。`--strict` は全 gate Pass のみ成功で Fail/NotRun/Blocked/Unsupported は exit 2（「失敗していない」と「合格」を混同しない）。

### 既知の境界と follow-up

各 GW slice で確定した follow-up・既知境界をまとめる。

- GW-02: `ScopedEffects` の実導出は GW-04（実施済み）、Approval receipt binding は GW-05/06（実施済み）。`ProactivePermit.condition` は opaque tag で条件の型化は GW-09/ポリシースキーマ設計へ。`GrantBinding::Session` は adapter 発行 session identity を `AdapterId` で表現し multiplex adapter は session ごとに別 ID を mint する契約が GW-08 待ち。
- GW-04: 残り `ProjectOp` 変数（parameter/automation/comp 系）の lowering は issue #56 範囲外の semantic capability として別 issue。`RegisterClockEpoch` は unsupported 宣言済みで、gateway resource model が clock epoch を観測できる resource kind を得たら lower+effect 化。
- GW-05: `midi.note.*` preview は `StructuredContentRead` を emission boundary で要求する。metadata-only の read grant は entity-level diff のみ許可する方針と整合するか GW-09 で再考。
- GW-06: gate 内 `Ledger` scope は `(principal-tag, project, key)` で GW-01 wire ledger の `(adapter, project, principal, key)` より狭い（adapter 次元なし）— 多 adapter 化の際は同一 fingerprint scope へ揃える必要。非 commit outcome は ledger settle→best-effort journal append の順で、同 process retry は durable 未確認の outcome を返し得る（restart 権威は常に journal）。replay 済み `Rejected`/`Indeterminate` は wire 上 `Denied{Commit}`/`Indeterminate` に正規化され元の `GatewayError` variant 忠実度は失われる（outcome であって variant ではない設計判断）。`ProjectController::load` は in-memory undo/redo stack をクリア（restart を跨いだ undo 継続は非対応）。host precondition として、controller `apply` 内の resource oracle/op 実装は controller mutex 保持中に gate へ再入してはならない（deadlock）。`ScheduledFence` は ordering 意味論は `MutexFence` と同一だが real timing race は完全に列挙しない（timing fuzz は別 issue #62 範囲外）。

### 再利用可能な検証・文書運用規約

review-protocol は独立 reviewer 2 系（A: 受入条件トレース / B: adversarial security/failure）を投入し、全 candidate をコード実測で個別検証（Validator）、確定した P0/P1 blocker を修正してから再検証（Judge）する運用である。各 IR に指摘→判定（Confirmed/Rejected/Doc/Recorded）→対応の表が残り、確定した指摘は `*_regressions.rs` に恒久検証として追加する。Rejected は設計意図の明文化、Recorded は非 blocking で follow-up 送りである。

決定的並行・故障検証では、`ScheduledFence`（thread-local label で commit section を park/resume、unlabeled は本番同様即実行）で revoke↔commit・concurrent commit の順序を確率的 race でなく決定的に列挙し、`CommitHooks`+`GateCrash` で authorize後/apply後/journal後の crash fault injection、real `FileJournal`/`DirectoryBundleStore`/`FilePolicyStore` への torn tail・kill→reopen fault injection、`ManualClock` で expiry 境界を決定的にテストする。

headless 検証の構造は `rig::compose()`/`GatewayStack`/`rig/mod.rs` の shared test rig で real `Gateway`/`GrantPolicy`/`ContextProjectionEngine`/`PrepareEngine`/`ProposalStore`/`ProposalGate`/`CommitGate`+journal を組み立て、fixture は scripted fault 注入（`fail_revoke_grants`）と live-revision 参照を持つ。`InMemoryPolicyStore`/`ManualClock`/`MemorySnapshotSource`/`FixtureAdapter`/`ProviderStub`/`MediaStub`/`ScheduledFence` で決定的 contract proof を得る。scripted double は fault *分類* の証拠であり実 durability 証拠ではない、という境界が繰り返し明記される。

文書チェーン規約は spec→design→plan→task→test-spec→impl-ir/impl-exp の 7 文書鎖 + `evidence/sv<N>/` 台帳で、index（各種 README）は生成物で `doc-maintenance`/`sync_impl_index` で再生成し手編集しない。canonical front matter（id/type/status/title/created/updated/owners/relations）と relations（implements/derived-by/verifies/references/depends-on/blocks/supersedes）の相互整合が要求され、scaffold 生成の slug 名は task 指定の canonical 名へ rename する運用である。

実行入口は `mise run fmt-check`/`check`/`lint`/`test`/`test-rt`/`test-msrv`/`check-headless-deps`/`verify-full`/`prek` である。`mise run gw10` は 9 gateway suite + real-transport suite + `gw10_report -- --strict` を実行し G0〜G6+GTV の 8 gate verdict を出す。`target/gw10-evidence/*.jsonl` は run 毎に増えるため `gw10` task は `--clean` から開始し stale Pass/Fail が集計を汚さない。verdict は `gw10_report -- --strict` の集約を正本とする。

evidence の正直性として、実行したコマンドのみを Pass として記録し、未再実行の package・未実行の check を明記して推測で補わない。`NotRun`/`Unsupported` を first-class verdict として記録し optional 欠測は gate を fail させないが記録は残す。headless/mock/PoC real transport の Pass を実機/GUI/Provider/第三者 Host 受入に繰り上げず、mock 層の PASS を実機証拠に読み替えない — layer/mode/backend/transport field が常に evidence の出所を示す。

構造的修正の優先として、「fix at the boundary that owns the invariant」に従い、第二 validator・第二 diff engine・第二 Policy/Project 正本・並行 authorization scheme を作らず、既存 `Operation::validate`/`GrantPolicy` internals/`ProjectController::apply`/`DerivedEffect` 射影を再利用する。unsupported/unknown/unconfirmed/indeterminate を型で明示し success/failure や absent data に collapse させない。

## 適用対象

この知識は Synvelis の Automation・Command Gateway・AUTX 系サブシステム全体に適用される。具体的には `synvelis-workspace`/`synvelis-project` の Automation headless 状態機械・曲線処理・録音 transaction、`synvelis-gateway` の capability 契約・認可・context projection・prepare/proposal/commit・job/media/provenance・MCP adapter、workspace 側 GUI projection と app 側 ViewSpec、CLI adapter、gw10 evidence harness にまたがる。外部 gate（実 GUI・実 plugin dispatch・実 provider・第三者 MCP host・実機 transport/RT・OS 電源断・cross-repo consumer 回帰）は NotRun/Unsupported として区別して扱う。
