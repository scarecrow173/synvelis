# CI と検証プロセス — 実行証拠

Synvelis の CI 基盤構築・lane 追加・evidence gate・impact 分類・sccache・npm freshness・CI flake 修正・tracker reconcile・stale vendor 診断、および製品側の検証 oracle 実装にわたる実行記録である。検証は GitHub Actions の実 run、`node --test` の契約 test、mise lane（fmt-check・check・lint・test・test-rt・test-msrv・lint-actions 等）、合成 jobs JSON の再生、fixture 再現実験で構成される。計画段階・未完了・NotRun の事項は実績と区別して記録する。task/plan の front matter status と IR の Validation 記録が一致しない箇所があり、その場合は「文書が一致しない」と記録してどちらかを正と断定していない。

## sccache 導入（synvelis#147）

sccache v0.19.0 を GitHub Actions cache backend で verify・gw10-verify（各 3 OS）に導入した。cold run 41823038077 で verify hit 1.35–9.05%・write errors 0–47（GHAC rate limit の既知挙動）でも fail-open で全 13 job green だった。warm run 41824169427 で hit 74.89–100%・errors 全 0、verify wall は Before 4 run 中央値を全 OS で下回る（ubuntu 112s・windows 223s・macos 177s）。warm run 2（41825678376）で hit 95.52–100% に収束し verify 95/222/112s、gw10 32/97/54s。kill switch `CI_SCCACHE_DISABLE=1` で sccache 4 step 全 skip・harness success を実測（変数は検証後削除）。rt-verify の RT 列挙コンパイルは 56s・本試験 4s を計測した。

## CI flake 修正（synvelis#154、#184、#245）

mcp-poc port flake（synvelis#154）では、直近 31 run（全て 2026-11-04、runNumber 1–31）で ConnectionReset flake を 3 件確認した。run 単位 ≈9.7%、delegated real-transport テスト実行単位 ≈0.9%（1 run あたり約 11 実行 × 31 ≈ 340 実行中 3 件）。失敗は run 41815380858（msrv-verify・`stdio_e2e::delegated_apply_commits_...`・`common/mod.rs:50` write ConnectionReset code 104）・41816354694（verify ubuntu・`gw10f_delegated_apply_commits_and_survives_restart_real`・Connection reset by peer、issue-147 exp でも記録済み）・41768184551（msrv-verify・同 gw10f test・`common/mod.rs:57` read ConnectionReset）の 3 件で、全て delegated-apply 系テスト（control channel TCP RPC を最も多く実行し hijack された接続が RST を受ける露出ウィンドウが最大）に集中した。code 104 `ConnectionReset` は TCP control channel でのみ発生し得るシグネチャ（Linux で stdio pipe への write は EPIPE code 32、read は EOF）。原因は `free_port()` probe→bind の TOCTOU + `control_listener` の silent return。

`--control-port 0` + stderr readiness 報告 + bind fail-closed へ修正後、`cargo test -p mcp-poc` 9/9 pass（stdio_e2e 5 + gw10_transport 4）・clippy `-D warnings`/fmt clean・占有 port で `control listener bind failed`（os error 10048）exit 1・port 0 で `control-port=53217` 報告を実測した。

PR #158 / run 41841675449（attempt 1、head `17f359f`、base `76afee6`、ruviform `8fb665f1`）の shadow 証跡で偽陰性 0: classify は changed 3・classes docs/gateway/ipc・affected=[mcp-poc]（leaf で downstream dependent なし）・fallback false、not-applicable 4 leg（rt-verify + ui-verify ×3）全て full 実行 pass で consistent、14 job green・msrv-verify 1m43s pass、evidence verdict `all expected lanes passed`。ruviform #238（`l1_proxy_e2e` flake）は別機構（shared-memory plugin 試験の wall-clock sleep 同期、Windows CI のスケジューリング遅延）で #241（`f6d6936` pipeline barrier 化）で解決済みであり、「実 process+実 transport の timing 依存を明示的同期へ置き換える」教訓の共有であって本件の直接原因ではない。

canonical temp fixture（synvelis#184）は plan approved で、本グループに実装記録はない。`TempTree::new` で `create_dir_all` 後に `fs::canonicalize` したパスを `Self { root }` に保持する修正計画であり、非 canonical temp 綴り（junction 経由 `TEMP`/`TMP`）で修正前に同一 4 件 FAILED を再現済み（対照実験として記録）。Windows の `\\?\` verbatim 形が他 API で問題になるリスクは design の実測済み範囲では問題なしと評価。GitHub-hosted `windows-latest` の TEMP が具体的にどの非 canonical 綴りかは runner イメージ依存で未確定だが原因クラスは確定。修正が実際に行われたかは不明。

macOS alloc flake（synvelis#245）では verify-macos run 42750871026 で `rt_event_enqueue_is_alloc_and_dealloc_free` が `allocations: 1 (64 bytes)`（期待 0）で flake した。warm-up を計測対象インスタンス自身へ変更する修正を実施し、fmt-check/check/lint/test/test-rt/test-msrv 全 exit 0（`rt_cache` 含む全テスト pass、MSRV rust 1.89.0 toolchain でも pass、補助証拠 `cargo test -p synvelis-library --test rt_cache` 1 passed）。
