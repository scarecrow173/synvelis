# オートメーション実行基盤とコマンドゲートウェイ — 実行証拠

この文書は、Synvelis の Automation 系（synvelis#131〜134・synvelis#6）、AUTX 系（synvelis#259〜267・synvelis#446）、Command Gateway 系（synvelis#45〜62）の検証・実行記録をまとめる。対象文書は計 69 件（実験記録 20・実装記録 33・計画 8・タスク 8。JSONL 2 件は event skim）である。canonical lane は `mise run <task>` であり、headless/mock/PoC real transport の Pass を実機・実 GUI・実 provider・第三者 host の受入に昇格させていない。計画文書は `approved`、タスク文書は `in-progress`/`todo`/`done` が混在し、いくつかの実装記録（IR）は `in-progress` のままだが対応する実験記録・検証節には緑の実測が記録されている。以下では IR/exp の実績記述を優先し、計画・タスク段階の記述は「計画」「タスク」として区別する。IR `completed` であっても内容が docs-only slice や headless 契約のみの場合は「文書作成の完了」「headless 検証済み」と読み、製品実装・実機受入の完了とはみなさない。

## 状態の齟齬・矛盾（明示）

- **IR in-progress vs 検証済み**: AUTX-04 atomic macro・AUTX-05 workflow DSL・AUTX-06 live adapters/mixed-source/workflow coordinator の 5 IR は front matter `status: in-progress`。ただし対応する exp 記録は completed/実測緑（82 tests・6/6 pass 等）を報告。status 更新が追従していない文書状態の齟齬であり技術的矛盾ではないが、「in-progress = 未完了」とは読めない。
- **Task status 未更新**: AUT-01 task1 は `in-progress`、AUT-04 task1 は `todo`（全チェックボックス未チェック）、AUTX-01-F01 task は `in-progress`（全チェック・検証済み）、command-gateway task は `in-progress`（Done When 全未チェック）。これらに対応する IR は全て completed で実測緑。plan 側も AUT-01〜04・automation-modulation・autx-01-f01・command-gateway は `approved` のまま。AUT-02/AUT-03/AUT-04 task・automation-modulation task・autx-08 task は done。
- **テスト数の別観測**: `test synvelis-gateway` は sv45 記録で 487、sv46 記録で 406 passed/0 failed/25 binaries。文書が「別観測であり混同しない」と明記しており両者は別 run の記録。GW-10 記録では 82 tests（gw10_* suite）+ real transport 4 tests。
- **AUTX-06 vs AUTX-08 の live adapter 範囲**: AUTX-06 live adapters IR は in-progress だが `GatewayStepLane` は AUTX-08 Leg C で production 組み立て・parity 検証済み（completed）。`GatewayJobLane` は依然 scope 外。live adapter の「実装済み」と「検証済み」の範囲が文書間で異なる。
- **GW-07 source.register 経路**: `synvelis.source.register`+`set-state` は caller 申告 digest で `Verified` に到達でき GW-07 media gate とは別経路。「verified evidence 必須」を `Verified` source 一般に適用するかは未裁定で別 issue 送り — 現状は「job 出力は gate 経由」のみが契約。
- **AUT-03 design 差分**: design は `SealOutcome.write_range_closed` を構想したが実装は `close_write_range() -> bool` + `TransportEffect.sealed` の 2 値で十分と判断し重複 outcome 型を導入しなかった。`set_loop` validation は close 前に評価（不正 range で recording を閉じない）。`pos < loop.start` の点は permissive lead-in として記録（半開区間契約は loop end 側で厳密）。
- **AUT-04 design 差分**: `drain_record_events` を `drain_record_event`+`drain_reject`+`fold_record_gaps`+`emit_drain_notifications` へ分割（clippy too_many_lines）。verbatim 縮約優先順位を design の分類順から「feature 点優先+残り先頭順」へ単純化（機能差なし）。
- **GW-07 テスト数の内部 drift**: file map は `tests/job.rs` 新規 17 テストと記載するが validation は 23/23 pass と記録（実装中の追加テストで増加したと推測されるが文書内で明示的な説明なし）。

## 未実施・Deferred・Unsupported（横断）

- 実 GUI/OS device・実 plugin・実 provider・第三者 MCP host・実 RT 負荷・OS 電源断・cross-repo consumer 回帰（CONSUMER-RUVIFORM/AUDIOLENS）は全 Gateway/Automation slice で NotRun/Unsupported。headless/mock/PoC real transport の Pass はこれらを含まない。`Product Accepted` は全 Gate で NotRun。
- `InMemoryPolicyStore`/`ProposalStore` は in-memory で restart で lifecycle 記録消失（durable verdict/消費は journal replay で復元されるが approval lifecycle は再 request 前提）。
- `FileJournal`/`FilePolicyStore` は real storage fault injection 済みだが fsync 嘘・silent bit rot は脅威モデル外。journal GC/checkpoint・複数 project multiplex は PoC 範囲外。
- `TypedRange` media range・pin/cursor per-principal quota・`MidiDivision` tagged 表現・candidate 列挙 O(project) lazy 化は GW-03 follow-up。`note_grant_revoked` wiring・`MediaGate` production 実装・MIDI output lane は GW-07 follow-up。Streamable HTTP/mutual-TLS・control listener の platform IPC 移行は GW-08 follow-up。real-device GUI render/focus/multi-window race・push subscription・GW-09 `preview_value` の Approval UI 接続は GW-09 follow-up。
- AUT-01〜04 の実 GUI Inspector/Window・実 plugin dispatch・実機 transport・AUT-F01 multi-pass take（synvelis#6、Unsupported）・実機 RT 録音・実 Browser/Canvas・永続曲線 Simplification は全て NotRun/Unsupported/Integration 対象。`note_graph_stale` は host 通知境界として新設されたが実 host 配線責務は呼出側にある（現状の in-crate 呼出は test のみ）。
- Ruviform 共通化評価（ruviform#553）・両 consumer 回帰（ruviform#294・synvelis#28・audio-lens#127）は評価専用・条件付きで本 slice 群では変更なし。
- GW 系 follow-up/risks: GW-02 の `ProactivePermit.condition` 型化は GW-09/ポリシースキーマ設計へ、`GrantBinding::Session` の multiplex adapter 契約は GW-08 待ち。GW-04 の残り `ProjectOp`（parameter/automation/comp 系）lowering は別 issue、`RegisterClockEpoch` は unsupported 宣言済み。GW-05 の `midi.note.*` preview の `StructuredContentRead` 要求は GW-09 で再考。GW-06 の gate 内 `Ledger` scope は wire ledger より adapter 次元が狭く多 adapter 化時に揃える必要、非 commit outcome は ledger settle→best-effort journal append の順（restart 権威は常に journal）、replay 済み `Rejected`/`Indeterminate` は wire 上 `Denied{Commit}`/`Indeterminate` に正規化（variant 忠実度は失われる設計判断）、`ProjectController::load` は undo/redo stack をクリア、controller `apply` 内の resource oracle/op は mutex 保持中に gate へ再入禁止（deadlock）、`ScheduledFence` は real timing race を完全には列挙しない（timing fuzz は synvelis#62 範囲外）。
